Built for teams tired of AI-at-runtime fragility.

Every browser agent in the market today invokes an LLM on every task. Claude for Chrome. Atlas. Browser Use. Stagehand. The ones that compile still let the LLM pick selectors freely. Every one of them has the same three architectural failure modes. Taprun fixes them at the architecture level.

Compile once.

AI runs exactly once — at authoring time. It captures the site's stable structural addresses (JSON-LD, OpenAPI, ARIA landmarks, RSS) instead of brittle CSS selectors the next deploy will wipe out. The compiled program is data, not code: a 25-op closed vocabulary that can't eval, can't spawn workers, can't reach the network outside declared endpoints.

"LLMs frequently generate CSS class selectors or XPath rather than Playwright's recommended getByRole / getByLabel / getByText approach, even when accessible-name selectors would work. The generated code can 'work' on first run but break on the first layout tweak." — jimmypk, HN discussion on a deterministic-automation launch, 2026-04-15

Run forever.

Zero LLM calls at runtime. Zero prompt-injection surface. Zero context-window loss. Zero tokens per execution. Same input → same output, every time. The compile-time captured structure becomes a boring, deterministic playback — which is exactly what production workloads want.

"same input → different outputs / works in testing → breaks randomly in production / retries magically 'fix' things. The agent wasn't wrong. The environment was inconsistent. The biggest improvement I made wasn't prompt tuning. It was stabilizing the execution environment." — r/AI_Agents, "Most agent problems are actually environment problems", 2026-04-07

Diff the drift.

tap doctor compares the captured fingerprint against the live page and flags structural drift before your data goes stale. tap fix proposes an AI-written patch on Pro. tap refresh re-baselines only after a human approves. Lifecycle as a first-class primitive — not an afterthought retry loop.

"I'd be curious whether you measure success as 'initial generation works' or 'the same flow still passes after small DOM/layout changes a week later' — that's the boundary between a neat demo and something a team can rely on." — potter098, HN, 2026-04-15 (question left unanswered by the compile-only competitor)

Local-first vs Cloud-first browser SDKs

The same task, two architectures. The trust boundary lives in different places.

Concern Cloud-first SDK
(Stagehand+Browserbase, Apify, Browserless)		 Taprun
(local-first by architecture)
Where do logged-in cookies live? On the cloud vendor's servers Only in your local browser
What does the AI see? Full session + your data on every run Only the page DOM during forge time (one-time)
Compliance with TOS / robots.txt Vendor signs ToS for you (or you for them) Your account, your terms — by you
Internal / intranet sites Need VPN tunneling into the cloud Just open the page (already on your network)
What happens if the vendor goes down? Your scrapers stop Local code keeps running
Plan format portability Locked to vendor SDK .tap.json data — version, grep, audit, port

FAQ

Questions worth asking before you install.

What does "compile once" mean?
AI runs once at authoring time to capture a site's stable structural addresses (JSON-LD, OpenAPI, ARIA, RSS) — not to generate fragile CSS selectors. The compiled program is then replayed deterministically, no LLM at runtime.
What happens when the site changes?
Run tap doctor. It compares captured fingerprints against the live page and flags drift — before your data goes stale. On Pro, tap fix proposes an AI-written patch; tap refresh rebaselines after human approval.
Is my data safe?
Everything runs on your machine. Programs are structured data plans (closed 25-op vocabulary), not arbitrary JavaScript. No runtime eval, no new Worker, no cloud exfiltration. See SECURITY.md in the public repo.
